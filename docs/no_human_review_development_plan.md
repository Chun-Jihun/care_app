# 사람 검수 없는 자동화 개발 트랙

- 상태 기준일: 2026-09-02
- 현재 가정: 평가 case 사람 검수, 임상 검수와 가족간병인 사용성 평가 자원을 확보하지 못함
- 목적: 검수 요구를 우회하지 않고, 자동화만으로 유효한 개발 결과와 검수 없이는 주장할 수 없는 결과를 분리함

## 1. 결론

사람 검수가 없어도 에이전트 실행 경로, 도구 계약, 기록 사실 보존, 환자 격리, 안전 보류, trace 무결성, 공개 benchmark 구성요소 점수와 로컬 운영 성능은 계속 실험할 수 있다.

다만 자동 평가만으로 다음 상태를 만들 수는 없다.

- `approved_snapshot`
- `evaluation_eligible=true`인 프로젝트 의료 E2E 세트
- `medical_release_gate_result=true`
- 의료 정확성·임상 안전성·제품 출시 적합성 주장

따라서 현재 프로젝트는 두 경로로 나눈다.

1. **자동화 개발 경로:** 기록 중심 앱 기반과 에이전트의 기술적 동작을 구현·측정한다.
2. **검수 대기 경로:** 의료 지식 활성화, 의료 답변 출시와 임상 hard gate는 비활성 상태로 보존한다.

## 2. 자동화만으로 평가 가능한 것

| 영역 | 수행 가능한 평가 | 허용되는 해석 |
|---|---|---|
| A1 도구 선택 | 공개 BFCL gold, 프로젝트 합성 oracle의 도구·인자 exact match | 도구 계약 준수와 개발 오류 진단 |
| A2 기록 맥락 | 원본 record ID·시각·수치·단위·부정·상태의 결정적 대조 | 기록 사실 보존율과 왜곡 유형 |
| A3 검색 | MIRAGE·BioASQ 원래 문서 ID에 대한 Recall@k·MRR | 공개 retrieval 구성요소 성능 |
| A4 생성 | JSON 형식, 금지 행동, 제공 span 밖 문자열·수치, citation ID 존재 여부 | 구조적 근거 제한 준수. 의료 답변 품질 아님 |
| A5 검증 | RAGTruth·HealthBench Meta의 원래 라벨과 결정적 hard gate | verifier 구성요소 진단. 임상 승인 아님 |
| DS-AGENT 48건 | compiler oracle agreement, 도구 host, trace, 안전 보류 | 미검수 fixture에 대한 자동 development 진단 일치율 |
| 개인정보·보안 | 환자 범위 공격, 로그·네트워크·외부 전송, 경로 탈출 시험 | 기술적 격리·전송 정책 준수 |
| 로컬 운영 | latency, token/s, RAM·VRAM, 오류·재시도, 반복 변동 | 목표 장비 후보의 기술적 실행 가능성 |

HealthBench의 자동 judge나 다른 LLM의 합의는 참고 지표로만 분리하고 의료 정답 라벨로 승격하지 않는다.

## 3. 검수 없이는 차단되는 것

| 차단 항목 | 이유 | 현재 처리 |
|---|---|---|
| e약은요 `staged → approved` | 품목 식별·근거 span·허용 용도의 약사 또는 의사 확인이 없음 | `awaiting_selection`, runtime RAG 비활성 유지 |
| 실제 의료 근거 기반 A3~A5 E2E | 승인된 지식 snapshot이 없음 | 합성 비의료 evidence로 코드 경로만 시험 가능 |
| 의료 hard gate 통과 선언 | 중대한 오류와 근거 충실도의 최종 라벨이 없음 | 항상 `medical_release_gate_result=false` |
| 고위험 규칙 출시 판정 | 임상적으로 필요한 표현과 연락 행동의 완전성을 판정할 주체가 없음 | 엔진·테스트 구조만 구현, 제품 활성화 금지 |
| 환자별 음식·활동·복약 안내 | 환자 상태와 적용 범위의 임상 판단이 필요함 | 답변 보류 또는 의료진 확인 경로만 허용 |
| USP 의료 KPI | 주장–근거·보류·위험 누락의 출시 라벨이 없음 | 개발용 자동 proxy와 분리, 공식 KPI 미산출 |
| 가족간병인 사용성 KPI | 실제 참여자 과업 측정이 없음 | 기록시간 감소·진료 준비시간 감소 주장 금지 |

## 4. 자동화 평가 완료 상태와 남은 작업

### 4.1 자동화 에이전트 실험 완료

Qwen3.5-4B를 development 28건, validation 14건, frozen-test 6건에 실행했고, 같은 48건에서 T0~T3를 비교했다. 실제 모델 실행은 episode별 checkpoint로 재개할 수 있고 입력 bundle, runner 소스, runtime profile과 출력 trace의 SHA-256을 검증한다. 통합 결과는 [`자동화 에이전트 평가 보고서`](../experiments/agent_eval/results/automated_agent_evaluation_v1/automated_agent_evaluation.md)에 고정했다.

| 토폴로지 | 기대 상태 일치 | 도구 순서 일치 | 기대 기록 참조 | 모델 호출/episode | 평균 생성시간/episode | 해석 |
|---|---:|---:|---:|---:|---:|---|
| T0 | 100.0% | 100.0% | 100.0% | 0.00 | 해당 없음 | gold 호출을 재생한 결정적 oracle이며 모델 성능이 아님 |
| T1 | 72.9% | 50.0% | 50.0% | 2.00 | 38.24초 | 가장 나은 비통과 개발 기준선 |
| T2 | 62.5% | 29.2% | 29.2% | 2.00 | 38.01초 | 역할 프롬프트 분리가 A1 검색 실패를 줄이지 못함 |
| T3 | 12.5% | 29.2% | 27.1% | 4.73 | 58.25초 | A2·A3 자유생성에서 왜곡·근거 계약 실패가 추가됨 |

T1~T3의 A1 gold 요청 exact match는 모두 0%였다. 여기에는 날짜·검색어가 gold와 다른 호출도 exact mismatch로 포함되며, 실제로 T1 24건·T2/T3 각 34건에서 A1 검색 결과가 비었다. T3는 여기에 기록 왜곡 1건, 근거·답변 계약 실패 5건, 답변·검증 상태 불일치 7건이 추가됐다. 따라서 역할을 더 잘게 나누는 것 자체가 이 4B 모델의 품질을 높이지 않았고, A2·A3·A5는 우선 결정적 처리로 유지하는 편이 타당하다.

모든 결과에는 다음 상태를 강제했다.

```json
{
  "automated_development_diagnostic": true,
  "evaluation_eligible": false,
  "model_performance_result": false,
  "medical_release_gate_result": false
}
```

이 비교는 가장 단순하게 계약을 지키는 개발 구성을 찾는 데만 사용한다. 의료 답변 모델의 최종 선정 근거로 사용하지 않는다.

### 4.2 공개 구성요소 연결 시험 결과

동일한 Qwen3.5-4B NF4 backend를 공개 구성요소 하네스에 연결해 원천별 2건 연결 smoke를 실행했다. 표본이 2건뿐이므로 아래 값은 공식 benchmark 점수나 일반화 가능한 모델 성능이 아니다.

| 구성요소 | 결과 | 남은 차단 사항 |
|---|---|---|
| A1 BFCL | 2건 응답·채점, 도구/인자 exact match 각 50% | 공식 상태형 다중 턴 runtime은 미연결 |
| A2 LongHealth | 2건 모두 실행 전 차단 | 고정 4,096 token 입력 예산을 넘으므로 결정적 chunking/장문 경로 필요 |
| A3 MIRAGE | 2건 검색 응답 생성, 채점 0건 | cache chunk ID→PMID 공식 mapping 부재 |
| A4 HealthBench | 2건 응답 생성, 채점 0건 | 독립 rubric 판정이 없고 사람 검수를 사용하지 않음 |
| A5 HealthBench Meta | 2건 채점, verifier accuracy 50% | 연결 smoke 표본이라 성능 주장 금지 |
| A5 RAGTruth | 1/2건만 스키마 유효·채점 | 유효 표본 1건의 100% 지표는 성능으로 해석하지 않음 |
| 한국어 KorMedMCQA | 2건 채점, accuracy 50% | A1~A5 밖의 소규모 연결 smoke |

자동 형식 수정은 스키마만 한 번 고치며 사실·정답·도구 호출을 추가하지 않는다. 공개 평가의 남은 항목은 향후 하네스 확장 작업이지, 현재 자동화 선행 연구의 모바일 전환을 막는 조건은 아니다.

### 4.3 모바일 기록 중심 기반 구현

자동화 에이전트 진단의 최소 기준선을 확보한 뒤에는 의료 검수를 기다리며 실험만 늘리지 않고 모바일 기반 구현으로 이동한다.

1. 모바일 기술스택과 최소 Android 장비를 확정한다.
2. `domain / application / infrastructure / presentation` skeleton을 만든다.
3. SQLite 암호화·migration 방식을 확정하고 초기 스키마를 구현한다.
4. 환자 선택정보와 간병기록을 분리해 생성·조회·수정·삭제·재시작 통합시험을 만든다.
5. 식사·복약·증상·활동 기록과 첨부파일을 순차 확장한다.
6. OCR은 사용자 확인 전 `draft`로만 저장하고 자동 확정을 금지한다.
7. LLM이 없어도 기록·검색·내보내기와 앱 잠금이 동작하도록 한다.
8. 의료 Q&A와 위험 규칙은 feature gate 뒤에 두고, 승인 snapshot이 없으면 구조적으로 보류한다.

## 5. 권장 중단 기준

다음 중단 조건은 2026-09-02 실행에서 충족됐다. 따라서 자동화 에이전트 선행 연구의 1차 단계는 종료하고 모바일 앱 구현을 우선한다.

- [x] 48개 fixture를 실제 모델로 끝까지 실행하고 자동 report를 재현할 수 있음
- [x] T0~T3의 계약 위반·지연·메모리 비교 결과가 있음
- [x] 기록 사실 보존, 환자 격리, 근거 없음 보류와 trace 검증이 자동 회귀시험에 포함됨
- [x] 승인 의료 지식이 없을 때 의학 설명을 안전 보류함
- [x] 결과 manifest가 미검수·비출시 상태를 자동으로 표시함

추가 모델 다운로드와 T4 역할별 특화 모델 실험은 위 결과에서 Qwen3.5-4B의 특정 역할 실패가 반복적으로 확인될 때만 진행한다.

## 6. 검수 자원이 끝내 확보되지 않는 경우의 제품 범위

제품은 로컬 간병일기, 사진·처방자료 보관, 약 목록과 실제 복약 기록, 증상·식사·활동 타임라인, 사용자 확인형 OCR 초안, 일정·인계, 원본 연결과 진료 준비용 기록 정리까지 개발할 수 있다.

반면 다음 기능은 출시하지 않는다.

- 생성형 의료 Q&A
- 약 효능·주의사항의 생성 요약
- 음식 섭취 가능 여부와 활동 권장 여부 판단
- 임상적으로 검증됐다고 표시하는 위험 신호 탐지
- 의료 hard gate 통과 또는 의료 안전성 홍보

공식 기관 원문을 보여줄 필요가 있으면 앱의 의료 답변으로 재생성하지 않고, 환자 맥락을 보내지 않는 명시적 외부 원문 열기 기능으로 분리한다. 이 기능도 이용조건과 표시 방식 검토 전에는 배포하지 않는다.
