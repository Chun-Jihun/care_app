**간병수첩 기획 의도·문서·구현 검토 — 2026-09-07**

검토 기준은 사용자가 설명한 ‘환자 본인·가족·동거인 등 일상 돌봄을 하는 사람이 기록 부담을 줄이고, 진료 설명을 보존하며, 약·보조제·활동에 관한 의문을 이해하도록 돕는 모바일 앱’이다. 제품 요구사항 원문 전체를 읽고 유스케이스, 모바일 스키마, 모델·데이터·평가·승인 계획, 핵심 실행·검증 코드, 테스트와 기존 실험 보고서를 대조했다.

**판정: 제품 방향은 대체로 맞지만, 현재 성과는 앱 구현보다 텍스트 에이전트 연구 기반에 집중되어 있다. 입력을 쉽게 만드는 핵심 경험은 아직 검증되지 않았고, 답변 검증과 평가 코드에는 재현 가능한 결함이 있다.**

설계된 기능, 구현된 실험 도구, 실제 제품에서 검증된 기능을 구분해야 한다. 모바일 앱이 아직 없다는 사실 자체를 출시된 기능의 버그로 취급하지 않는다. 반면 아래 R1~R3는 현재 실험 코드에서도 실제로 발생하는 문제다.

**R1 · P1 — 최종 답변에서 복용 여부를 뒤집어도 검증을 통과한다**

- 위치: `scripts/ds_agent_tool_host.py:1103`의 `record_summary` 검사, `scripts/ds_agent_model_runner.py:1479`의 호출 경계.
- 원인: 검증기에 원본 사실 대신 허용된 기록 ID 집합을 전달한다. `care_entry_ids`가 존재하는지만 확인하므로 실제 기록과 주장 문장의 시각·수치·부정·복용 상태를 대조할 수 없다. A2 중간 결과를 검증해도 이후 A4가 내용을 다시 바꾸는 것은 잡지 못한다.
- 재현: 기존 합성 fixture의 원본은 `intake_status=taken`이다. A4의 답변과 claim 문장을 ‘평가용 기록약은 복용하지 않았다고 기록되어 있습니다.’로 바꿔 T1을 실행하면 A5는 `decision=pass`, 최종 상태는 `record_answer`가 된다.
- 영향: 사용자가 가장 신뢰해야 하는 실제 복약 기록의 의미가 최종 설명에서 뒤집힐 수 있다. 이는 요구사항 6.11의 원본 사실 보존과 A5 계약 9.1의 5~6번 검사를 충족하지 못한다.
- 수정 방향: 원본 버전과 정형 사실을 최종 검증 단계까지 전달한다. 복용 상태·시각·수치·단위처럼 결정적으로 표현할 수 있는 기록은 검증된 필드로 문장을 조합하고, 자유 생성 문장도 동일 사실을 보존한 경우에만 표시한다. 우선 `taken/missed/refused/unknown`, 시각·단위 변경과 부정 반전 회귀시험을 추가한다.

**R2 · P1 — 표시 문장과 claim 목록이 연결되지 않아 무근거 의료 설명이 통과한다**

- 위치: `scripts/ds_agent_tool_host.py:1073` 이후 claim 순회, `scripts/ds_agent_model_runner.py:1560` 이후 A4 원문 표시.
- 원인: 모델이 스스로 `claims`에 등록한 항목만 근거를 검사한다. `short_answer` 등 실제 표시 필드의 핵심 내용이 모두 claim에 대응하는지는 확인하지 않는다. 금지 표현 정규식은 모든 무근거 효능 설명을 포괄하지 않으며, `medical_answer_required`는 현재 episode의 `scenario_kind`에 의존한다.
- 재현: 의료 근거가 없는 기록 조회 episode에서 정상 기록 claim은 그대로 두고, `short_answer`에 가상의 약 효능 문장만 추가했다. A5는 `pass`였으며 추가 문장도 `user_visible_output`에 남았다. `claims=[]`로 비우고 잘못된 기록 답변을 표시하는 경우도 통과했다.
- 영향: ‘승인 근거가 없는 의료 내용은 생성하지 않는다’는 경계가 기록 질문 경로에서 우회된다. 현재 재현은 합성·고정 출력이며 실제 모델에서의 발생 빈도를 뜻하지 않는다.
- 수정 방향: 검증된 claim 및 정형 원본에서 표시 문장을 조합하거나, 모든 표시 문장과 claim의 위치·연결을 강제한다. 모델이 지정한 claim 종류만으로 의료 여부를 결정하지 않는다. 근거가 없는 기록 모드에서는 자유로운 의료 설명을 표시할 수 없게 한다. 유효한 근거 ID가 있어도 그 내용이 주장을 직접 뒷받침하는지 별도로 검사해야 한다.

**R3 · P2 — 답변에 기록을 사용하지 않아도 ‘기록 참조’와 전체 평가가 통과한다**

- 위치: `scripts/ds_agent_model_runner.py:1620`, `scripts/run_ds_agent_model.py:151`.
- 원인: `referenced_records`에 최종 답변이 실제 인용한 기록 대신 A2에서 확보한 `allowed_records` 전체를 넣는다. 채점기는 이 목록에 기대 ID가 포함되어 있는지만 검사한다.
- 재현: A4를 ‘질문을 확인했습니다.’, `claims=[]`로 바꾸고 정해진 검색·상세조회 순서를 실행했다. 기록 사실을 답하지 않았는데도 `expected_records_referenced=true`와 `all_expected_checks_passed=true`가 되었다.
- 영향: 검색에 성공했다는 지표가 답변에 기록을 반영했다는 지표처럼 집계된다. 기존 62.5%는 현재 구현의 구조적 검사 결과이며 유용한 답변 성공률로 해석할 수 없다. 기존 보고서가 의료 성능으로 확대 해석하지 않은 것은 적절하다.
- 수정 방향: 검색으로 확보한 ID, 생성 입력으로 제공한 ID, 검증된 최종 문장에서 사용한 ID를 분리한다. 답변 참조 지표는 마지막 집합으로 채점하고 원문 사실 보존과 질문 과업 완료도 별도 검사한다. 지표·검증 코드 수정 후 영향받은 평가를 다시 실행해야 한다.

**D1 — 음성 지원을 ‘질문 입력’에서 ‘기록 작성과 진료 설명 보존’으로 구체화해야 한다**

요구사항 `FR-04`는 음성 질문을 권장 기능으로 두고, 유스케이스 `UC-18`은 음성 질문과 설명 이해 확인을 묶는다. 음성 구조화 초안과 `voice` 출처는 이미 있으므로 완전히 누락됐다고 할 수는 없다. 그러나 ASR/STT의 입력·출력·보관·확인·실패 계약과 독립 평가가 없다. 모델 평가 역시 텍스트 SLM과 OCR/VLM에 집중되어 있다.

다음 흐름을 별도 유스케이스로 정의할 필요가 있다.

1. 짧은 음성 메모 → 로컬 전사 → 식사·복약·활동 등 여러 기록 후보 → 원문 대조·사용자 확인 → 저장.
2. 진료 후 받아 적은 설명 또는 허용된 진료 음성 → 전사 원문 → 의료진 설명·할 일·질문 초안 → 사용자 확인 → 진료 기록과 원본 연결.

ASR은 소리를 문자로 옮기고 SLM은 그 문자를 항목별 초안으로 정리하는 역할로 구분한다. 문서/이미지 OCR도 SLM과 독립된 입력 구성요소로 평가한다. 약명·숫자·단위·부정 오류, 중간 녹음 중단, 여러 화자, 불명확한 구간, 하나의 발화에 여러 사건이 있는 경우를 사전 시험에 넣는다. 실제 음성 보관 여부와 기간, 진료 녹음 범위는 구현 전 사용자 선택과 제품 정책으로 확정해야 하며 이 검토에서 임의로 확정하지 않았다.

**D2 — 새 약·건강보조제의 조합 확인은 일반적인 약 설명과 별도 과업이다**

문서에는 약-약·약-음식 상호작용의 원칙과 DB 초안이 있다. 하지만 사용자가 아직 복용하지 않은 제품을 후보로 등록하고, 현재 약 목록과 대조하며, 필요한 성분 정보가 없을 때 확인을 요청하는 흐름은 구체화되지 않았다. 건강보조제·건강기능식품·비타민의 제품 종류, 복합 성분과 식별 불확실성을 다루는 계약도 없다. 현재 여섯 읽기 도구에는 조합 확인 도구가 없고 `interactions`는 약 정보 조회의 섹션이다.

데이터 카탈로그 자체도 e약은요를 일반의약품 범위로 설명하고 모든 처방약을 포괄하지 않는다고 명시한다. DUR은 규칙 데이터 후보이며 후속 계약이다. 따라서 현재 확보한 자료나 약 설명 조회만으로 사용자의 ‘기존 약과 새 약/보조제 확인’ 과업을 해결했다고 평가할 수 없다.

제품 계약에는 현재 복용품과 검토 중인 후보를 구분하고, 확인된 제품·성분과 미확정 항목, 검토한 데이터의 범위·버전·출처를 보존해야 한다. 결과는 확인된 주의 근거, 정보 부족, 자료 범위 밖, 의료진·약사 확인 필요 등을 구분해야 한다. 조회 결과가 없다는 이유로 ‘함께 먹어도 안전함’을 만들지 않아야 한다. 이 앱의 현재 목적상 환자별 복용 허가나 처방 시작·변경 결론을 제공하는 방향으로 확대하지 않는다.

**D3 — 다음 개발의 중심은 실제 모바일 기록 과업이어야 한다**

현재 프로젝트 자체 코드는 데이터 수집·검수 패킷·평가 adapter·scenario compiler·도구 host·모델 runner·보고서 생성에 집중되어 있다. 모바일 화면, 암호화 저장, 앱 잠금, 카메라/마이크 입력과 기록의 재시작 복구를 끝까지 수행하는 앱은 없다. `InMemoryPilotRepository`는 실험용 저장소이며 모바일 암호화 DB 구현이 아니다.

이는 README도 명시한 개발 단계다. README의 ‘현재 최우선 작업’과 사람 검수 없는 개발 계획은 이미 연구의 1차 중단 기준을 충족했고 모바일 기록 기반으로 전환하라고 정리한다. 그 결정을 실행하는 것이 기획 의도에 맞다. 다만 README 20행에는 여전히 ‘연구 트랙을 최우선으로 전환’이라고 적혀 있어 57행의 현재 우선순위와 혼동된다. 과거 단계라는 표시로 정리할 필요가 있다.

다음 제품 완료 기준은 문서 수나 후보 모델 수보다 ‘직접 기록 → 앱 종료 → 재실행 → 조회·수정·삭제’, ‘사진/음성 → 확인 가능한 초안 → 저장’, ‘진료 설명 → 원문에 연결된 후속 할 일’의 완주 여부로 두는 편이 적절하다. 의료 검수 부재는 의료 답변 활성화를 막지만 로컬 기록 앱 구현을 막지는 않는다.

**D4 — 현재 실험은 제품 입력·질문 범위와 모바일 예산을 대표하지 않는다**

현재 48건은 24명의 합성 환자에 대해 복약 event 24개에서 만든 기록 조회 24건과 근거 없음 보류 24건이다. 컴파일러 입력도 `medication_intake`로 제한한다. 원천 이미지·음성·실제 약 근거는 없으며, `safety_gate_result`는 컴파일된 상태의 `continue` 값이다. runner가 이를 읽어 분기하는 것은 구현되어 있지만 원문 위험 표현을 판정하는 임상 규칙 엔진의 검증은 아니다. 이 제한은 개발 진단으로서 의도적이며 현재 실험을 무효로 만들지는 않는다.

추가로 필요한 제품 시험은 다중 날짜/다중 기록, 식사·활동·진료 설명, OCR/STT 오류 수정, 여러 기록을 만드는 발화, 미등록 새 제품, 데이터 범위 밖 보조제, 여러 환자 전환, 오프라인 저장·복구다. 고위험 임상 출시 판정은 기존 요구사항대로 검수 자원 확보 후 진행한다.

저장된 모델 비교 보고서에서 Qwen3.5 T1의 8건은 현재 검사상 5/8 통과, 평균 생성시간 39.8초, 최대 VRAM 3.53 GiB다. Windows/RTX 3060 Ti 실험이며 모바일 측정값이 아니다. 이 수치로 휴대전화에서 불가능하다고 단정할 수도, 충분히 빠르다고 판단할 수도 없다. 최소 기기·허용 메모리·모델 다운로드 크기·저장공간·음성/사진 처리시간·발열·배터리 기준을 먼저 정하고, 기록 저장은 추론 완료와 독립적으로 동작하게 해야 한다. SLM·OCR·ASR을 모두 사용하는 앱 전체의 자원 비용을 측정해야 한다.

**D5 — 사용자 범위와 활동 안내의 제품 표현을 다듬을 필요가 있다**

‘가족·비전문 간병인’은 동거인을 배제하는 구현 규칙은 아니지만, 환자 본인이 자신을 기록하는 경우와 돌봄 제공자가 다른 사람을 기록하는 경우가 액터·대표 시나리오에서 드러나지 않는다. 작성자와 기록 대상자를 구분하고, 자기 돌봄에서도 불필요한 가족 초대나 관계 입력 없이 같은 기록 기능을 쓸 수 있다는 요구를 명시하는 것이 좋다. 이는 가족 공유 기능을 앞당기자는 뜻은 아니다.

활동은 현재 요구사항 `FR-16`처럼 의료진 지시와 승인 자료 범위의 일반 원칙·확인 조건으로 안내하는 방향이 맞다. 사용자가 기대하는 ‘운동 추천’을 새 치료·재활 처방으로 해석하지 말고, 이미 받은 지시 확인·수행 기록·관련 승인 정보 이해의 과업으로 구체화해야 한다.

**유지할 설계와 구현**

- 간병기록을 MVP에서 암호화해 지속 저장하고, 선택적인 식별정보와 분리한 설계.
- OCR/VLM 결과의 초안·사용자 확인, 실제 복약과 처방 일정의 구분, 의료진 지시 출처·이력, 요약의 원본 버전 연결.
- 환자 범위를 모델 인자가 아니라 host에서 고정하고 도구 역할·예산·허용 ID를 검사하는 구현.
- staged 자료와 승인 지식의 분리, 변경된 파일/검수 패킷의 해시 검사, 승인 이후에도 런타임 활성화를 별도 통제하는 구현.
- 공개 benchmark, 합성 개발 진단, 의료 성능·출시 판정을 구분하고 자동 결과로 임상 승인 상태를 만들지 않는 원칙.
- 검수자 부재에도 기록 중심 개발을 계속하되 의료 답변 활성화는 막는 계획. 사용자가 원한 질문 도우미를 완성하려면 콘텐츠 검수 자원은 별도로 해결해야 한다.

**권장 수정 순서**

1. R1~R3의 실패 입력을 회귀시험으로 고정하고 최종 답변 검증·평가 집계를 수정한다. 수정 전 지표를 답변 정확도나 제품 채택 근거로 사용하지 않는다.
2. 요구사항 원문에 환자 본인·동거인, 음성 일기, 진료 설명 보존, 검토 중인 약·보조제 확인 과업을 반영하고 FR→UC→데이터→시험 연결을 맞춘다. 정하지 않은 녹음·보관·플랫폼 정책은 별도 결정 항목으로 남긴다.
3. 최소 모바일 대상과 암호화 저장 구성을 정하고 직접 기록·재시작·조회·수정·삭제의 작은 완성본을 만든다. 안전 실패 시험을 기능 구현보다 먼저 작성한다.
4. 동일 기록에 사진 OCR과 음성 전사 입력을 연결하고 초안 확인까지의 시간·수정량·원문 보존을 측정한다. 진료 설명에서 할 일과 질문을 만드는 흐름을 포함한다.
5. 새 약·보조제 확인과 활동 안내에 필요한 승인 데이터·규칙·검수 범위를 확보한 후 제한된 질문 도우미를 활성화한다. 그전에도 사용자가 후보 제품·증상·의료진 질문을 기록하고 원문을 찾는 기능은 개발할 수 있다.

**이번 검증의 증거와 한계**

`python -m unittest discover -s tests -v` 결과: **94개, 전부 통과**. 현재 작업공간의 로컬 fixture와 보고서 산출물이 존재하는 환경에서 실행했다. 새 환경에서의 설치·재생성 검증은 수행하지 않았다.

별도로 기존 테스트의 합성 저장소와 scripted backend를 사용해 아래 네 입력을 T1 전체 실행 경로에 주입했다. 실제 모델의 오류 빈도를 측정하는 실험이 아니라, 잘못된 출력이 왔을 때 검증기가 차단하는지 확인하는 반례 시험이다.

| 입력 변형 | 기대 | 실제 |
|---|---|---|
| 원본 `taken`, 최종 답변은 ‘복용하지 않음’ | 왜곡 차단 | `pass`, `record_answer` |
| 의료 근거 없는 기록 질문의 표시 문장에 가상 효능 추가, claim에는 미등록 | 무근거 내용 차단 | `pass`, 추가 문장 표시 |
| 잘못된 기록 답변에 `claims=[]` | 주장 연결 누락 차단 | `pass` |
| ‘질문을 확인했습니다.’만 답하고 `claims=[]` | 기록 답변 성공 평가 실패 | 네 expected check와 전체 검사 모두 통과 |

모바일 실기기 시험, OCR·ASR 실행, 실제 모델 재추론, 의료 원문 내용·법률·라이선스의 최신 외부 검증은 수행하지 않았다. 기존 실험 수치는 저장된 보고서를 근거로 인용했다. 현재 위험 규칙·의료 성능이 임상적으로 검증됐다고 판단하지 않았다.

검토 중 제품 요구사항과 구현 코드는 수정하지 않았으며 이 보고서만 추가했다. 시작 시 존재하던 두 실험 결과 디렉터리의 미추적 파일도 수정하지 않았다.
