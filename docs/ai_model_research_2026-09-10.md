## 1. 권고

**추가 학습은 유력한 개선 수단이지만, 현재 결과만으로 세 모델 모두에 지식증류가 필요하다고 결론 내릴 수는 없다.** 먼저 동일한 간병 과업으로 후보를 비교하고, 입력 처리·검색·출력 계약을 개선한 뒤 남는 오류에 학습을 적용한다.

이번 조사에서 권하는 첫 비교 구성은 다음과 같다. 아래 우선순위는 공식 자료와 프로젝트 제약을 바탕으로 한 설계 판단이며, 이 앱에서 측정한 모델 순위가 아니다.

| 기능 | 첫 비교군 | 우선 개선할 부분 | 학습에 들어갈 조건 |
|---|---|---|---|
| 챗봇 | 기존 Qwen3.5-4B, 작은 Qwen3.5-2B, 새 Gemma 4 E2B | 날짜·환자 범위·검색의 호스트 처리, 간단한 출력 계약, 승인 근거 연결 | 같은 유형의 의도·필드 추출·원문 보존·보류 오류가 구조 개선 뒤에도 반복됨 |
| OCR | PP-OCRv5 mobile 검출기 + 한국어 전용 인식기. 다른 문자권은 해당 인식기로 비교 | 촬영 품질, 문서 영역·행 분리, 약명·숫자·단위의 원문 위치 연결 | 촬영·검출이 정상인데 특정 글꼴·약명·숫자 인식 오류가 반복됨 |
| 음성 전사 | Whisper base/small 다국어판, Qwen3-ASR-0.6B. SenseVoiceSmall은 이용 조건을 확인한 추가 비교군 | 음성 구간 검출, 언어 선택, 긴 녹음 분할, 원문과 정규화 분리 | 약명·고령자 발화·생활 소음 오류가 입력 처리 후에도 반복됨 |

챗봇·OCR·ASR을 하나의 멀티모달 모델에 모두 맡기는 구성도 비교할 수 있지만 첫 구현의 기본값으로 삼지 않는다. 각각의 오류를 원문에 대조하기 쉽고, 필요한 모델만 메모리에 올릴 수 있는 구성을 먼저 측정한다. 음식명 후보 인식은 OCR과 다른 과업이며, 음식 사진만으로 재료·섭취량·환자별 섭취 안전성을 확정하지 않는다.

## 2. 현재 프로젝트에서 실제로 확인된 사실

### 기존 실험의 의미

[로컬 모델 비교 V1](../experiments/agent_eval/results/model_comparison_v1/model_comparison.md)은 동일한 합성 개발 사례 8건에서 다음 결과를 기록했다.

| 모델 | 전체 계약 통과 | 평균 모델 생성 시간/사례 | 관찰된 주요 문제 |
|---|---:|---:|---|
| Qwen3.5-4B | 5/8, 62.5% | 39.8초 | 일부 기록 검색 및 최종 상태 불일치 |
| Qwen3-4B-Instruct-2507 | 0/8 | 35.4초 | 한국어 기록과 맞지 않는 영어 검색어 등으로 기록을 놓침 |
| EXAONE-4.0-1.2B | 0/8 | 33.2초 | 필수 JSON 항목을 누락하고 형식 수정 후에도 반복 |

이는 의료 정답률이 아니다. 자동 생성한 개발 사례이며 사람·임상 검수 전이다. 기대 의료 근거 ID가 비어 있어, 해당 검사 100%를 근거 검색 성능으로 해석할 수도 없다. MedGemma와 Nanbeige는 역할 계약 연결 시험 각 1건만 실행했으므로 위 8건 순위에 넣지 않는다. 실패한 1건만으로 모델 전체의 의료·언어 능력을 판정하지 않는다.

[기존 구성 비교](../experiments/agent_eval/results/automated_agent_evaluation_v1/automated_agent_evaluation.md)의 동일 48건에서는 T1의 기록 참조율 50.0%, 평균 지연 약 38.2초에 비해 T3는 27.1%, 약 58.2초였다. 이 제한된 실험에서는 생성 역할을 늘리는 이득이 관찰되지 않았다. T0의 100%는 정답 도구 요청을 재생하는 oracle 기준선으로, 실제 사용자 질문을 코드만으로 100% 해결했다는 결과가 아니다.

현재 [고정 런타임](./qwen35_local_runtime_decision.md)은 Windows·RTX 3060 Ti 8GB·Transformers·bitsandbytes NF4이며, Qwen 선형 attention은 PyTorch reference 구현을 사용했다. 따라서 위 지연을 모델 자체의 최선 성능이나 휴대전화 지연으로 일반화할 수 없다. NF4 추론을 했다는 사실은 QLoRA 학습을 했다는 뜻도 아니다.

현재 앱에는 실제 챗봇·OCR·ASR 모델이 연결되지 않았다. 확인한 모델 평가 결과에도 처방자료 OCR 및 간병 음성 전사의 성능 측정은 없다. 두 과업은 기준선부터 만들어야 한다.

### 학습 이전에 분리해야 할 원인

| 관찰 | 첫 대조실험 | 결과에 따른 조치 |
|---|---|---|
| 올바른 기록을 못 찾음 | 동일 질문에 정답 검색 범위를 제공했을 때 답변 가능한지 비교 | 검색·질의 변환 문제와 답변 모델 문제를 분리 |
| 필수 JSON 항목 누락 | 동일 모델·입력으로 출력 문법 제약 적용/미적용 비교 | 문법으로 해결되면 학습 필요성 감소. 값의 의미는 별도 검사 |
| 기록을 받았는데 수치·부정 의미가 변함 | 정답 기록을 직접 제공하는 생성 단독 시험 | 추출형 표시를 우선하고, 남는 오류를 표적 학습 후보로 분류 |
| 출력이 느림 | 호출 수, 프롬프트 길이, 생성 길이, 엔진, 양자화를 각각 바꿔 비교 | 어느 요인이 시간을 쓰는지 확인 후 경량화 |
| OCR 약명이 틀림 | 올바른 행 crop을 인식기에 직접 제공 | 검출/잘림 문제인지 문자 인식 문제인지 분리 |
| 음성에서 단어가 사라짐 | 원음과 VAD 분할본, 자동 언어와 지정 언어를 각각 비교 | 음성 구간 누락·언어 오판과 ASR 자체 오류를 분리 |

## 3. 챗봇 후보

| 후보 | 확인된 특징 | 앱에 대한 판단 |
|---|---|---|
| **Qwen3.5-2B** | 공개 instruction 모델, Apache-2.0. 기본 non-thinking 모드와 다국어 지원. 공식 카드도 작은 크기의 용도로 과업별 튜닝·개발을 제시한다. | 기존 4B와 같은 계열에서 메모리·지연을 줄일 수 있는지 보는 학생 모델 후보. 더 작아서 정확도가 좋아진다는 의미는 아님 |
| **Qwen3.5-4B** | 기존 로컬 실행·계약 비교 이력이 있는 기준선 | 구조 개선 효과를 측정하는 대조군. 휴대전화 채택은 별도 판정 |
| **Gemma 4 E2B**, 필요하면 E4B | Apache-2.0. 도구 호출, system 역할, 선택적 thinking, 텍스트·영상·음성 입력 지원. E2B는 유효 2.3B이나 embedding 포함 5.1B, E4B는 유효 4.5B이나 embedding 포함 8B로 표기 | 새 모바일 비교 후보. 이름의 E2B를 일반적인 총 2B 모델로 보고 저장용량을 계산하면 안 됨 |

출처: [Qwen3.5-2B 모델 카드](https://huggingface.co/Qwen/Qwen3.5-2B), [Qwen3.5-4B 모델 카드](https://huggingface.co/Qwen/Qwen3.5-4B), [Gemma 4 모델 카드](https://ai.google.dev/gemma/docs/core/model_card_4).

Gemma 4는 최신 LiteRT-LM 문서에서 Android와 iOS 실행 경로를 확인했다. 다만 Swift API는 Early Preview, Flutter 경로는 Community로 표시되어 있다. 공식 소개의 E2B 파일 크기는 약 2.58GB이며, 이 수치는 앱 전체 RAM이 아니다. 공식 최신 기기 성능을 사용자의 SM-S926N 성능으로 대입하지 않는다. [LiteRT-LM 공식 안내](https://developers.google.com/edge/litert-lm/overview).

Qwen은 llama.cpp의 GGUF 실행 경로를 우선 검토할 수 있다. Android 빌드와 Apple XCFramework 문서가 있지만, 사용할 모델 revision·변환기·엔진 버전·GPU backend 조합은 별도 실행 시험이 필요하다. 기존 데스크톱 NF4 파일을 그대로 모바일에 배포하는 계획은 아니다. [llama.cpp 공식 저장소](https://github.com/ggml-org/llama.cpp).

더 최신 이름만 따라가지는 않는다. 조사일의 Qwen3.8 공개 목록에는 27B·180B 등 큰 모델이 포함되어 있으며, 현재 휴대전화 우선 비교군과 자원 조건이 다르다. 이런 모델은 향후 교사 후보로 별도 평가할 수 있지만, 지금 확보한 8GB GPU에서 충분히 운영할 수 있다고 가정하지 않는다. [Qwen 공식 모델 목록](https://huggingface.co/Qwen).

### 챗봇이 배울 일과 코드가 처리할 일

1. **호스트가 환자 범위와 날짜 계산을 강제한다.** 모델은 의도와 필요한 슬롯을 제한된 형식으로 제안하고, 검색 범위·허용 ID·도구 인자는 코드가 검증한다. 명확한 날짜·기록 종류 조회는 생성 호출을 생략하는 경로도 새 기준선으로 비교한다. 모호한 표현은 확인을 요청한다.
2. **검색과 생성을 따로 개선한다.** 한국어 원문 표현을 유지한 어휘 검색, 승인된 동의어, 구조화 필터를 먼저 대조한다. 필요하면 다국어 임베딩 검색과 결합하고 재순위화를 적용하되, 선택 수첩·승인 문서 범위를 넘기지 않는다. 검색기 recall과 답변의 근거 충실도를 따로 측정한다.
3. **문법으로 출력 형식을 제한한다.** JSON Schema/grammar로 필수 항목·허용값을 제한한다. 모델에도 출력 구조의 의미를 설명한다. 문법이 맞아도 잘못된 약명·날짜·근거 ID는 나올 수 있으므로 호스트 검증은 유지한다. llama.cpp가 지원하는 JSON Schema는 일부이므로 실제 계약 변환과 실패 동작을 시험한다. [GBNF 및 JSON Schema 공식 문서](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md).
4. **의학 지식의 원본은 승인된 자료와 규칙이다.** 약물 상호작용·용량·위험 임계값을 모델 가중치의 기억으로 판정하지 않는다. 검수된 구조화 데이터가 포괄하지 않는 건강보조제·상호작용에 대해서는 '문제 없음'으로 결론 내리지 않는다.
5. **학습 목표는 앱의 행동이다.** 기록에서 사실 추출, 원문 시각·수치·부정 보존, 주장과 실제 근거 연결, 자료 부족 시 보류, 간결한 다국어 설명을 학습한다. 일반 의료 QA를 많이 주입하는 것을 첫 학습 목표로 잡지 않는다.

## 4. OCR 후보와 개선

**한국어 처방자료의 첫 후보는 `PP-OCRv5_mobile_det`와 `korean_PP-OCRv5_mobile_rec` 조합이다.** 한국어 인식기는 한국어와 영어를 지원한다. 중국어 간체·번체와 일본어는 해당 지원 인식기를 선택한다. 한국어가 기본 인식기에 자동 포함된다고 가정하지 않는다. [PP-OCRv5 공식 다국어 문서](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.en.md).

| 비교 후보 | 사용할 이유 | 확인할 제약 |
|---|---|---|
| **PP-OCRv5 mobile + 한국어 인식기** | 공개 인식기 가중치와 학습 경로가 있어 국내 약 봉투·글꼴에 맞춘 조정 가능 | 공식 on-device 안내는 Android CPU 경로. iOS 및 한국어 모델의 변환·연산자·문자 사전 일치는 별도 확인 |
| **PP-OCRv6 tiny/small 계열** | 조사 시점에 공개된 새 경량 계열. 다른 문자권의 속도·정확도 비교 후보 | 공식 통합 언어 목록은 중국어·영어·일본어·라틴 문자권 중심이며 한국어 지원을 확인하지 못함. 한국어 인식기의 자동 대체 후보로 선정하지 않음 |
| **ML Kit Text Recognition v2** | Android/iOS에서 한국어·일본어·중국어·라틴 문자를 처리하는 SDK 기준선 | 사용자 데이터 처리는 기기 내부지만 사용량·성능 지표의 Google 전송이 명시됨. 자체 가중치 튜닝 경로도 없어 현재 앱에 자동 도입하지 않음 |
| **PaddleOCR-VL-1.6 / Qwen 계열 VLM** | 표·레이아웃이 복잡한 자료의 비교 또는 보조 추출 | 휴대전화 비용과 숫자 누락·추가 생성·원문 좌표 연결을 검증해야 함. 자유 생성 결과를 처방 원본으로 취급하지 않음 |

근거: [PaddleOCR on-device 배포 안내](https://paddlepaddle.github.io/PaddleOCR/main/en/version3.x/deployment/on_device_deployment.html), [PP-OCRv6 소개](https://www.paddleocr.ai/latest/en/version3.x/algorithm/PP-OCRv6/PP-OCRv6.html), [PaddleOCR 공식 저장소의 현재 모델](https://github.com/PaddlePaddle/PaddleOCR), [ML Kit 문자 인식](https://developers.google.com/ml-kit/vision/text-recognition/v2), [ML Kit 개인정보 처리 안내](https://developers.google.com/ml-kit/terms).

구현·평가 순서는 다음과 같이 제안한다.

1. 촬영 중 흐림·반사·작은 글자·잘림을 확인하고 재촬영 또는 영역 지정을 돕는다. 과도한 이진화로 소수점이 사라지는지도 대조한다.
2. 문서 방향·원근과 텍스트 검출을 처리한 뒤 행 단위로 인식한다. 원본 이미지와 좌표를 보존한다.
3. 인식 문자열과 필드 추출을 분리한다. 약명·함량·횟수·시점마다 원문 영역, 추출 상태와 불확실성을 연결한다. 엔진 점수를 보정 없이 '정확할 확률'로 표시하지 않는다.
4. 사전은 확인할 후보를 제안하는 데 사용한다. 비슷한 약명으로 몰래 교체하거나 읽히지 않는 숫자를 문맥으로 채우지 않는다. `0.5`와 `5`, `mg`와 `mL`, 약 하나의 용법이 다른 행으로 넘어가는 오류를 별도로 검사한다.
5. 사용자가 확인한 뒤 초안에서 확정 기록으로 전환한다. 모델 간 결과가 같다는 이유로 사용자 확인을 생략하지 않는다.
6. 인식기 자체의 반복 오류가 남으면 정답 행 이미지로 해당 인식기를 미세조정한다. 이후에도 더 작은 인식기가 필요할 때 검증된 큰 인식기의 출력을 활용한 증류를 검토한다. 한국어를 지원하는 교사를 사용하며, 다른 언어용 PP-OCR의 증류 설정을 무검증 복사하지 않는다.

전용 소형 OCR을 비교할 근거는 PP-OCRv5·v6의 연구에서도 확인된다. 다만 논문의 자체 OCR 데이터 점수는 국내 처방전 필드 정확도나 이 앱의 성능이 아니다. [PP-OCRv5 논문](https://arxiv.org/abs/2603.24373), [PP-OCRv6 논문](https://arxiv.org/abs/2606.13108).

[Distil-Whisper 모델 카드](https://huggingface.co/distil-whisper/distil-large-v3.5), [Moonshine 공식 저장소](https://github.com/moonshine-ai/moonshine).

처음에는 한 사람이 말하는 짧은 기록 입력을 기준으로 평가하고, 진료실 긴 대화는 소음·화자 겹침·의사/환자 발화 구분을 포함한 별도 과업으로 평가한다. 짧은 메모에서 성공했다고 진료 전체를 정확하게 받아적는다고 표시하지 않는다.

- VAD로 음성 구간을 찾되 작은 목소리, 문장 끝의 '안 했어요' 등이 잘리지 않는지 확인한다. 무음·TV·음악을 넣었을 때 존재하지 않는 기록 문장을 생성하는지도 시험한다.
- 사용자가 말할 언어를 선택할 수 있게 하고 자동 감지와 비교한다. UI 언어를 발화 언어로 강제하지 않는다.
- 긴 녹음은 겹치는 구간과 시각을 두고 나누되 중복·누락을 검사한다. 실제 streaming 지원과 구간별 반복 인식을 구분한다.
- 원문 전사와 날짜·숫자 표기 정규화, 기록 필드 추출을 별도 결과로 유지한다. LLM의 자연스러운 교정이 약명·용량·부정을 바꾸지 못하게 한다.
- runtime이 지원하면 약명 후보 등을 인식 힌트로 비교하되, 힌트에 있는 약을 실제로 말하지 않았는데 추가하는 오류도 측정한다. 모든 엔진에서 같은 hotword 기능을 제공한다고 가정하지 않는다.
- 약명·수량·단위·복용/미복용의 핵심 부분은 해당 음성을 재생해 확인할 수 있어야 한다. 단어 시각은 모델마다 별도 정렬기가 필요할 수 있고, 잘 맞는 시각 자체가 단어 정답을 보장하지 않는다.
- 녹음·전사 보관은 기존 사용자 선택 정책에 맞춘다. 실제 진료 녹음을 기본 학습 데이터로 수집하거나 외부 교사 API로 보내지 않는다.

## 6. 미세조정과 지식증류를 적용하는 방법

### 서로 다른 도구다

| 방법 | 바꾸는 것 | 이 프로젝트에서의 순서 |
|---|---|---|
| 입력 처리·검색·출력 제약 | 모델 가중치 밖의 처리 과정 | 먼저 비교. 관찰된 검색·형식 오류에 직접 대응 |
| SFT | 정답 예시를 통해 모델의 과업 수행 행동 | 정답이 명확한 앱 과업의 반복 오류에 적용 |
| LoRA / QLoRA | 전체 가중치 대신 작은 adapter를 학습하는 방식. QLoRA는 양자화한 기반 모델을 고정해 학습 메모리를 줄임 | SFT를 적은 자원으로 수행할 후보. 그 자체로 모델 파라미터 수나 추론 시간이 줄어드는 것은 아님 |
| 출력 기반 증류 | 큰 교사의 검증된 출력을 작은 학생의 학습 정답으로 사용 | 교사가 해당 과업에서 충분히 잘하고 학생보다 나을 때 |
| 분포·logit 기반 증류 | 교사와 학생의 출력 확률 분포를 맞춤 | 메모리·tokenizer 호환·구현 부담을 감당할 근거가 생긴 뒤 |
| 양자화 및 양자화 인지 학습 | 저장·연산 정밀도와 그에 따른 오차 | 무학습 양자화 대조부터. 배포 정밀도에서 품질이 떨어질 때 추가 학습을 검토 |

QLoRA는 제한된 GPU에서 미세조정을 실험할 방법론이다. 원 논문의 메모리 절감 결과를 현재 Qwen/Gemma와 8GB GPU에서의 실행 보장으로 해석하지 않는다. [QLoRA 논문](https://arxiv.org/abs/2305.14314).

MiniLLM은 생성 모델의 분포 기반 증류 방법을 제시하지만, 현재 앱은 우선 검증 가능한 출력 예시를 이용하는 증류가 구현·추적 측면에서 단순하다는 판단이다. 교사·학생의 모델 계열과 tokenizer가 달라도 텍스트 예시를 이용하는 실험은 가능하지만, logit을 그대로 비교하는 구현은 별도 정렬 문제가 있다. [MiniLLM 논문](https://arxiv.org/abs/2306.08543).

ASR에서는 큰 모델이 만든 임시 전사를 품질 기준으로 걸러 학생 학습에 사용하는 Distil-Whisper 방법을 참고할 수 있다. 이때 약명·수치·부정이 틀린 전사를 그대로 정답으로 쓰면 중요한 오류를 학생에게 전수한다. 논문의 속도·오류율 개선 비율을 한국어 간병 전사에 적용된 수치로 제시하지 않는다. [Distil-Whisper 논문](https://arxiv.org/abs/2311.00430).

### 이 앱에 맞춘 학습 절차 제안

1. **오류 목록을 먼저 고정한다.** 검색 조건, 필수 필드, 원문 사실 보존, 근거 없음, 언어 혼합, OCR/ASR의 중요 숫자 등으로 나눈다. 과도한 보류도 오류로 측정한다.
2. **작은 지도학습 실험부터 한다.** 챗봇은 우선 수백~수천 개의 중복 제거한 과업 예시로 학습 곡선을 확인한다. 예시 수는 품질 보장 기준이 아니며, 자동 합성만 사용하면 결과를 개발 진단으로 제한한다. 학습량·언어 비율을 늘릴 때 기존 과업의 망각도 검사한다.
3. **교사는 과업별로 고른다.** 기록 행동은 더 큰 instruction 모델, OCR은 해당 문자권을 잘 읽는 인식기, ASR은 실제 전사 평가에서 나은 모델을 사용한다. 교사가 더 크다는 이유만으로 정답으로 간주하지 않는다.
4. **학습 예시를 검증한다.** 도구 예시는 결정적 실행 결과·환자 경계·원본 ID로, OCR/ASR은 정답 전사와 중요한 필드로 검사한다. 의학적 설명의 정답 승인은 의료진 검수가 필요하며 다른 LLM의 동의로 대신하지 않는다.
5. **최종 답과 필요한 행동을 학습한다.** 긴 추론 원문을 기본 학습 목표로 잡지 않는다. 원본 연결이 있는 간결한 결과와 보류 조건을 우선한다. 유창함만 높아지고 사실 보존이 낮아지면 채택하지 않는다.
6. **원본→학습본→모바일 변환본을 따로 평가한다.** adapter 병합 여부, 양자화, tokenizer·chat template·decoder 설정과 runtime을 기록한다. 프롬프트·모델·검색 변경 시 요구사항의 회귀시험을 실행한다.

현재 RTX 3060 Ti 8GB에서는 텍스트 전용 소형 모델의 짧은 문맥·작은 batch·gradient checkpointing을 이용한 adapter 실험부터 메모리를 측정하는 편이 현실적이다. 전체 멀티모달 학습, 대형 교사와 학생 동시 적재, 긴 진료 녹음 학습까지 가능하다고 약속할 수 없다. 학습은 개발 환경에서 수행하고 휴대전화에는 검증된 추론 파일을 배포하는 구성을 우선한다.

## 7. 데이터와 평가 설계

### 데이터 출처와 분리

- **앱 행동:** 현재 합성 DS-AGENT는 개발·실패 분석에 활용한다. 새 학습용과 최종 평가용은 서로 다른 시나리오·표현·가상 기록으로 분리한다. 이미 살펴본 8건·48건은 최종 미관측 시험으로 재사용하지 않는다.
- **OCR:** 직접 작성한 개인정보 없는 문서와 다양한 촬영 조건으로 초기 오류를 찾는다. 기존 카탈로그의 [AI Hub 의약품·화장품 패키징 OCR](https://aihub.or.kr/aihubdata/data/view.do?currMenu=115&dataSetSn=633&topMenu=100)은 추가 후보지만 처방전 전체 레이아웃과 다른 데이터다. 파일 접근·학습·재배포 조건을 확인한 후 사용한다. 실제 처방자료는 적절한 권한·비식별 처리·정답 검수 경로를 마련한다.
- **ASR:** 동의받은 비민감 시나리오 읽기와 자연스러운 말 바꾸기를 사용한다. 음성 합성만으로 테스트를 구성하면 고령자·소음·실제 발음 오류를 대표하지 못한다. [FLEURS](https://huggingface.co/datasets/google/fleurs)는 지원 언어의 일반 음성 기준선으로 참고할 수 있으나 진료실·약명 전사 검증을 대신하지 않는다.
- **의료 근거:** 이번에 검색한 웹페이지는 모델·방법론 조사 자료다. 운영 의료 지식베이스에 추가하거나 `staged` 자료를 `approved`로 바꾸지 않는다.
- **오염 방지:** 환자/가상 기록 묶음, 화자, 문서 원본·서식·증강 계열을 단위로 분할한다. 같은 문서의 다른 crop, 같은 발화의 다른 잡음 버전을 학습·시험에 나누지 않는다. BFCL·HealthBench·프로젝트 동결 평가 정답을 학습에 섞지 않는다.
- **권리 기록:** 코드, 기반 가중치, 변환 가중치, 데이터, 교사 출력 이용 조건을 각각 기록한다. 모델 라이선스가 학습 데이터와 교사 출력의 권리까지 해결하지 않는다.

| 챗봇 | 신규 200건 안팎의 기록 조회·추출·요약·보류·범위 공격 사례. 기존 48건은 디버그 회귀용 유지 | 실제 과업 성공, 검색 누락, 필드·인자 정확도, 수치·부정 보존, 원본/근거 연결, 잘못된 답변과 불필요한 보류, p50/p95 지연 |
| OCR | 서로 다른 문서 200장 안팎. 약 봉투·처방전·포장지 및 흐림·반사·잘림 사례를 구분 | 문자 오류율, 약명·용량·단위·횟수별 완전 일치, 잘못 연결된 행, 사용자 수정률·완료 시간 |
| ASR | 여러 화자의 짧은 발화 200개 안팎과 긴 대화·무음·소음 대조군 | 언어별 CER/WER, 약명·숫자·단위·부정 오류, 없는 발화 생성, 화자 혼동, RTF, 사용자 수정 시간 |

RTF는 처리 시간÷음성 길이로 기록하고, 반대 방향의 속도 배수와 혼동하지 않는다. 문자 오류율의 공백·문장부호 정규화 규칙을 고정하되 중요 숫자·부정은 정규화로 차이를 지워 채점하지 않는다.

한국어를 먼저 분석하되 영어·일본어·중국어 간체·번체를 독립적으로 평가한다. 다국어 평균으로 한 언어의 실패를 가리지 않는다. 간체·번체는 문자 표기이고 발화 언어·방언 선택과 다르며, 원문 전사와 표시 변환도 분리해야 한다. UI의 다국어 지원을 AI의 동일 품질 보장으로 표시하지 않는다.

### 구현 전에 고정할 실패 시나리오

| 실패 | 통과 조건 |
|---|---|
| 잠금·수첩 전환·원본 삭제 중 모델 결과 도착 | 결과 표시·저장 차단, 엔진 취소 전달, 임시 민감 데이터 정리 |
| 이미지/녹음의 지시문이 시스템 정책을 바꾸려 함 | 입력 자료로만 취급, 허용 도구·환자 범위 확장 없음 |
| 약명·소수점·단위·부정 인식이 불확실함 | 원문 재확인 경로, 사용자 확인 없는 확정 0건 |
| 승인 근거가 없거나 충돌함 | 추측한 의료 설명·복용 변경·안전 확정 0건 |
| 위험 표현이 전사·요약에서 누락됨 | 원문에 우선 적용하는 규칙과 출력 검사. 임상 적합성은 별도 검수 |
| 메모리 부족·모델 손상·지원 안 되는 언어 | 명확한 기능 실패와 수동 입력 복귀, 기존 기록 유지 |
| SDK/모델 로더가 네트워크나 원문 로그 사용 | 승인되지 않은 원본·기록·식별정보 전송 0건, 네트워크·로그 실제 검사 |

현재 사람·임상 검수 자원이 없다는 요구사항은 그대로 적용된다. 자동 합성 결과의 `compiler_generated_unreviewed`, `evaluation_eligible=false`를 유지하며, 자동 평가 통과만으로 의료 답변 기능을 활성화하지 않는다.

## 8. 모바일 통합과 자원 검증

현재 [ContextTasks](../mobile/lib/application/context_tasks.dart), [NotebookContextReader](../mobile/lib/domain/notebook_context.dart), [DraftService](../mobile/lib/application/services/drafts_service.dart)의 경계를 활용한다. 챗봇은 제한된 읽기 문맥, OCR은 사용자가 선택한 이미지, ASR은 해당 입력 작업의 음성만 받아야 한다. OCR·ASR 입력을 처리하기 위해 전체 저장소나 복호화 키를 모델 어댑터에 넘기지 않는다.

추후 `ChatInference`·`OcrEngine`·`SpeechTranscriber` 같은 좁은 포트를 추가하는 방향을 제안한다. 이는 현재 존재하는 구현 이름이 아니다. 모델별 전처리·토큰화·native binding은 구현 계층에 두고, 결과 DTO에 원문 위치·모델 버전·미확정 상태를 담는다. 기록 확정 명령과 추론 결과 반환은 분리한다.

`ContextTask`는 현재 늦은 결과를 버리지만 native 라이브러리의 계산을 강제로 중단하지는 않는다. 실제 엔진을 연결할 때 취소 신호, 메모리·파일 수명, 마이크 중단을 함께 구현하고 시험해야 한다.

모바일 비교에서는 다음을 기록한다.

- 기존 검증 기기 SM-S926N / Android 16부터 cold/warm 실행, 모델 로딩 시간, 첫 결과와 전체 결과 시간, peak RAM·GPU 사용량·저장용량을 측정한다. 하위 기기와 iOS는 별도 판정한다. [기존 Android 시험 기록](./android_device_validation_2026-09-10.md).
- 모델의 광고상 최대 문맥 대신 앱 과업에 필요한 문맥·출력 길이로 시험한다. 문맥 제한 때문에 중요한 원문을 조용히 자르지 않는다.
- 같은 모델의 원 정밀도, 가능한 8비트 및 모바일 4/5비트 변환본을 대조한다. 4비트에서 중요 필드 보존이 떨어지면 더 높은 정밀도나 다른 모델을 선택한다.
- OCR·ASR·LLM의 동시 적재와 순차 적재를 비교하고 메모리 압박·발열·연속 작업 후 지연을 측정한다. 통과하지 못하는 기기에는 수동 입력을 유지한다.
- 모델 파일의 출처·revision·hash·변환 절차·라이선스를 고정한다. 손상·업데이트 중단 시 기존 파일로 돌아가는 경로를 둔다. 초기 실험은 검증된 파일의 로컬 제공을 사용하며, 모델 다운로드 기능은 별도 배포 설계가 필요하다.
- 공개 runtime의 iOS 지원과 이 앱의 iOS 검증 완료를 구분한다. 현재 Mac/Xcode가 없어 iOS 실행 결과는 아직 없다.

## 9. 다음 실행 순서

1. **현재 실험의 실패를 재분류하고 새 평가 입력·정답·분할을 고정한다.** 기존 출력과 프로필은 보존한다.
2. **챗봇 3종, OCR 한국어 전용 조합, Whisper/Qwen ASR의 기준선을 만든다.** 같은 데이터·판정 규칙을 쓰고 실행 불가·미지원 언어는 0점과 구분해 기록한다.
3. **입력·검색·계약을 개선한 대조실험을 수행한다.** 정답 기록/정답 crop/정답 분할을 제공하는 시험으로 병목을 찾는다.
4. **모바일로 변환 가능한 후보를 실제 기기에서 측정한다.** PC 점수만 높은 후보에 먼저 학습 비용을 쓰지 않는다.
5. **남는 오류에만 SFT/LoRA 또는 OCR·ASR 미세조정을 적용한다.** 학습 전후의 의미 보존과 언어별 회귀를 비교한다.
6. **작은 후보가 자원 조건은 맞지만 품질이 부족하고, 검증된 교사가 확보되면 증류한다.** 교사의 정답성·학습 데이터 권리·의료 검수 경계는 유지한다.

이 조사 문서 작성 단계에서는 기존 코드와 고정 모델 프로필을 바꾸지 않았으며 모델 다운로드·학습·새 성능 시험을 수행하지 않았다. 이후 승인받아 실행한 비교와 개선 대조시험은 [후속 기준선 실험 결과](./ai_baseline_results_2026-09-10.md)에 별도로 기록했다.
